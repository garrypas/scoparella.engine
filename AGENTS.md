# Repository instructions

## Source of truth

This file is the canonical source of project-specific agent instructions. Other instruction files, including `CLAUDE.md`, should reference this file rather than duplicate its guidance. If instructions conflict, follow this file.

## Project overview

- This is a TypeScript Scopa game engine published as `@garrypas/scoparella.engine` to GitHub Packages.
- Production source is under `src/`; generated build output is written to `dist/`.
- Jest with `ts-jest` runs unit tests (`*.spec.ts`) and acceptance tests (`*.acceptance.ts`) using separate configuration files.
- For Scopa rules, tactics, variants, or rule-related code changes, consult the [Scopa game skill](.claude/skills/scopa-game/SKILL.md). It distinguishes common tabletop rules from this engine's behavior.
- When code behavior or public APIs change, update the relevant documentation and agent instructions/skills as appropriate so they remain consistent with the implementation. If they conflict, code is authoritative; document the discrepancy rather than silently describing behavior the code does not implement.

## Development

- Install dependencies with `npm ci` so the checked-in `package-lock.json` remains authoritative.
- Build with `npm run build`.
- Run unit tests with `npm test` and acceptance tests with `npm run test:acceptance`. Both test scripts build before running Jest.
- Run both test suites after changes that affect application behavior or public APIs.
- Follow the existing TypeScript style (two-space indentation, single quotes) and compiler constraints in `tsconfig.json`, including strict null checks, no implicit `any`, and no unused locals.
- Add or update tests alongside the relevant source area. Unit tests use `*.spec.ts`; acceptance tests use `*.acceptance.ts` and `jest.config.acceptance.js`.
- Do not hand-edit `dist/`; it is generated by the build. Keep `package-lock.json` in sync with dependency or package metadata changes.
- Preserve existing public behavior unless the task explicitly asks for a behavior or API change.

## CI and publishing

- `.github/workflows/build.yml` runs the build, unit tests, and acceptance tests on pushes and pull requests targeting `master`.
- `.github/workflows/publish.yml` publishes to `https://npm.pkg.github.com` after a successful Build workflow on a push to `master`, using the workflow's `GITHUB_TOKEN`.
- Before a change intended to publish a new package release, update the package version and keep the lockfile metadata synchronized. Never add credentials to the repository.
